## 2. 배당 격자는 전수다

각 API는 당첨 조합만이 아니라 **배당판 전체 조합**을 준다. 조합 수와 행 수가
정확히 일치함을 여러 경주에서 확인했다.

| 경주 | 출주두수 n | API | 행 수 | 이론값 |
| --- | ---: | --- | ---: | --- |
| 2025-03-08 서울 1R | 11 | `API28_1` | 22 | 단승 n=11 + 연승 n=11 |
| 2025-03-08 서울 1R | 11 | `API29_1` | 220 | 쌍승 n(n-1)=110 + 복승 C(n,2)=55 + 복연승 55 |
| 2025-03-08 서울 1R | 11 | `API30_1` TRI | 990 | n(n-1)(n-2)=990 |
| 2025-03-08 서울 1R | 11 | `API30_1` TLA | 165 | C(n,3)=165 |
| 2016-09-25 서울 2R | 10 | `API30_1` TRI | 720 | 720 |
| 2016-09-25 서울 2R | 10 | `API30_1` TLA | 120 | 120 |
| 2021-05-15 서울 1R | 12 | `API30_1` TRI | 1,320 | 1,320 |

11두 경주 한 건의 7승식 전체 = **1,397행**.

### 취소마 처리

API는 **출주두수 기준**으로 조합을 만든다. 등록두수가 아니다.

2025-03-08 서울 하루 복승 `totalCount = 520`.
- 출주두수 기준 `Σ C(출주두수, 2)` = 520 → **일치**
- 등록두수 기준 `Σ C(등록두수, 2)` = 550 → 불일치

### 표시상한 9999.9

**API에도 `9999.9` 상한이 그대로 있다.** 배당판 HTML과 동일한 인코딩이다.
API로 검열 문제를 우회할 수 없다.

상한 셀 비율 예시:
- 2016-09-25 서울 2R 삼쌍승: 720셀 중 243셀
- 2025-03-08 서울 1R 삼쌍승: 990셀 중 477셀

### API 값과 HTML 배당판 값은 동일하다

무작위 표본(시드 20260818) 복승 셀 **804개를 소수점까지 대조한 결과 전부
일치**했다. 불일치 0, API에 없는 셀 0, 일치율 100.0000%.

두 출처는 같은 원천이며, HTML 기반으로 산출된 기존 분석 결과는 API 데이터로도
그대로 재현된다.

## 3. `numOfRows` 상한

**문서의 3,000은 실제 상한이 아니다.** 100,000까지 정상 수용된다.

```
numOfRows=  10000  →  10,000행 수신 (totalCount 115,356)
numOfRows=  20000  →  20,000행 수신
numOfRows=  50000  →  50,000행 수신
numOfRows= 100000  → 100,000행 수신
```

`rc_no`를 생략하면 하루 전체, `rc_month`를 쓰면 한 달 전체가 온다.
서울 2025-03 삼쌍승 한 달 = 115,356행.

**따라서 경마장 × 월 단위 수집이 가능하다.** 전 역사를 약 3,700회 호출로
받을 수 있다(6절).

## 4. 자료 제공 범위

각 API가 실제로 반환하는 최초 시점. 월 단위로 훑어 확인했다.

| 데이터 | 서울 | 제주 | 부경 | 영천 |
| --- | --- | --- | --- | --- |
| 매출액 | 1991-01 | 1993-04 | 2005-09 | 없음 |
| 단승·연승 | 2002-01 | 2002-01 | 2005-09 | 없음 |
| 복승·쌍승·복연승 | 2007-01 | 2007-01 | 2007-01 | 없음 |
| 삼복승 (TLA) | 2009-03 | 2009-04 | 2009-03 | 없음 |
| 삼쌍승 (TRI) | 2016-03 | 2016-03 | 2016-03 | 없음 |

`meet=4`(영천)는 **자료가 없다.** 다섯 API(삼쌍승·복승·단승·매출액·출전표)를
2019~2026년 각 연도로 조회한 결과 전부 `totalCount = 0`이었다. API 문서에는
영천 지원이 명시되어 있으나 실제 반환은 없다.

2007-01, 2002-01처럼 1월에 딱 맞춰 시작하는 것은 **승식 도입일이 아니라
자료 공개 경계**다. 복승·쌍승은 실제로는 훨씬 이전부터 시행됐다.

각 승식의 자료 시작 지점에는 시험 기록이 섞여 있으므로 5절을 함께 볼 것.

## 5. ⚠ API에 시험 기록이 섞여 있다 — 판별 방법

각 승식의 자료 시작 지점에 **경주 수가 극히 적은 고립된 개최일**이 나타난다.
확인 결과 이들은 **실제 경주가 아니라 시스템 시험 기록**이다.

### 확인된 시험 기록

| 승식 | 날짜 | 요일 | 서울 | 제주 | 부경 |
| --- | --- | --- | ---: | ---: | ---: |
| 삼쌍승 | 2016-03-15 | 화 | 5경주 | 3경주 | — |
| 삼쌍승 | 2016-03-17 | 목 | — | — | 1경주 |
| 삼쌍승 | 2016-06-29 | 수 | 5경주 | — | — |
| 삼쌍승 | 2016-07-21 | 목 | 1경주 | 1경주 | 1경주 |
| 삼복승 | 2009-03-11 | 수 | 1경주 | — | 1경주 |
| 삼복승 | 2009-04-01 | 수 | — | 3경주 | — |
| 복승·쌍승 | 2007-01-09 | 화 | 4경주 | 1경주 | — |

### 판정 근거 (2016년 7건 실측)

| 날짜 | 복승 배당셀 | 매출액 | 출전표 | 착순 |
| --- | ---: | ---: | ---: | ---: |
| 서울 2016-03-15 | 462 | **0** | **0** | **0** |
| 제주 2016-03-15 | 117 | **0** | **0** | **0** |
| 부경 2016-03-17 | 0 | 0 | 0 | 0 |
| 서울 2016-06-29 | 0 | 0 | 0 | 0 |
| 2016-07-21 (3장 전부) | 0 | 0 | 0 | 0 |
| 서울 2016-06-11 *(대조)* | 508 | **355억** | 118 | 118 |
| 서울 2025-03-08 *(대조)* | 520 | **259억** | 110 | 110 |

매출액·착순·출전표가 모두 0이다. **발매가 없었으므로 경주도 없었다.**

추가 신호가 하나 더 있다. **승식이 불완전하다.** 이 날짜들에는 삼쌍승 데이터가
있으나 복승은 0행이다. 실제 경주라면 7승식이 모두 발매되므로 나올 수 없는
조합이다. 삼쌍승 시스템만 시험했다는 해석과 일치한다.

삼쌍승은 2016-03 시험 이후 4·5월이 완전히 비어 있고 **2016-06-10(금)
제주·부경, 2016-06-11(토) 서울**부터 정규 발매가 시작된다. 알려진 도입일
2016-06-10과 일치한다.

### ⚠ 요일로 판별하지 말 것

**요일 필터는 쓰면 안 된다.** 공휴일이 일요일과 겹치는 경우 등으로 정규 요일을
벗어나 실제 경마가 시행되는 날이 있다. 요일 기준으로 거르면 **진짜 경주를
버린다.** 개최일은 KRA가 매년 시행계획으로 정하는 행정 결정이므로 외부에서
규칙으로 재구성할 수 없다.

### 판별 기준

| 신호 | 실제 경주 | 시험 기록 |
| --- | --- | --- |
| 매출액 (`API179_1`의 `amt`) | 수억~수백억 원 | **0 또는 행 자체가 없음** |
| 착순 (`API214_1`의 `ord`) | 존재 | **없음** |
| 출전표 (`API26_2`) | 존재 | **없음** |
| 승식 완전성 | 7승식 모두 존재 | 일부 승식만 존재 |
| 오버라운드 `Σ(1/O)` | 환급률과 정합 | 깨짐 |

**매출액이 있고 착순이 있으면 실제 경주다.** 요일과 무관하다. 이것은
대리변수가 아니라 판별하려는 것 그 자체이므로 예외가 생기지 않는다.
2016년 7건에서 이 기준이 요일과 무관하게 작동함을 확인했다.

### 수집기 요구사항

1. 개최일 판별은 **매출액·착순 존재 여부**로 한다. 요일은 참고 신호일 뿐이다.
2. **승식 완전성 검사**를 넣는다. 일부 승식만 있는 날은 플래그를 붙인다.
3. 걸러낸 날짜는 **삭제하지 않고 별도 테이블에 보존**한다. 판단이 바뀔 수
   있고, 제외 근거를 증명할 수 있어야 한다.

## 7. 함정: 서비스키 인코딩

공공데이터포털은 같은 키를 두 형태로 준다.

- **Decoding** — 원본. `+` `/` `=` 포함
- **Encoding** — 이미 URL 인코딩됨. `%2B` `%2F` `%3D` 포함

Encoding 키에 `curl --data-urlencode`나 `requests`의 `params=`를 쓰면 `%`가
`%25`로 이중 인코딩되어 **`SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 뜬다.**
키가 등록되어 있어도 그렇게 보인다.

**권장: Decoding 키를 저장하고 라이브러리의 자동 URL 인코딩에 맡긴다.**

### 오류 코드 구분

| 오류 | 의미 |
| --- | --- |
| `NO_OPENAPI_SERVICE_ERROR` | **경로가 틀렸다.** 키와 무관하므로 키 없이도 경로 존재 확인에 쓸 수 있다 |
| `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` | 경로는 맞고, 키 미등록 또는 인코딩 문제 |
| `SERVICE_KEY_IS_NULL` | 키 파라미터가 전달되지 않았다 |

### 오퍼레이션 이름 규칙

서비스와 오퍼레이션 **양쪽에 `_1` 접미사**가 붙는 경우가 많다.
포털 화면에는 오퍼레이션만 보이고 서비스 경로는 잘려 있을 수 있으니,
**미리보기 버튼으로 열리는 실제 URL을 확인**하는 것이 가장 확실하다.

2018년판 활용가이드 문서의 경로는 이미 낡았다
(예: 문서의 `API30/triplePredictionRateInfo` → 실제 `API30_1/triplePredictionRateInfo_1`).

## 8. 매출액 API의 부가 정보

`API179_1/salesAndDividendRate_1`은 경주당 7행(승식별)을 준다.

```json
{"amt": 413419800, "meet": 1, "odds": "⑪③⑥-1077.1",
 "pool": "삼쌍", "rcDate": 20250308, "rcNo": 1}
```

- `amt` — 승식별 매출총액(취급액)
- `odds` — 당첨 조합과 확정배당 (원문자 마번 + 배당)
- `pool` — 단식 / 연식 / 복식 / 쌍식 / 복연 / 삼복 / 삼쌍

### 환급률 검산 통과

파리뮤추얼 항등식 `n = t·S / (100·O)`로 역산한 마권 수가 정수로 떨어진다.

| 승식 | 매출액 S | 배당 O | 환급률 t | 역산 마권 수 |
| --- | ---: | ---: | ---: | ---: |
| 삼쌍 | 413,419,800 | 1,077.1 | 0.73 | 2,802 |
| 단식 | 21,591,100 | 12.2 | 0.80 | 14,158 |

**API의 매출액이 배당판의 매출총액과 같은 정의임이 확인된다.**

### 연승 cutoff k를 직접 관측할 수 있다

`연식` 행에 지급된 연승 배당이 모두 실린다.

```
"odds": "⑪-2  ⑥-2.5  ③-3.5"    → k=3
```

`복연` 행도 마찬가지로 세 쌍이 실린다. 등록두수·출주두수만으로는 부분식별에
그치던 연승 지급 기준을 **관측값으로 확정**할 수 있다.

## 9. 기존 아카이브(v3) 대조에서 드러난 사실

2016-06~2025-12 구간을 HTML 스크레이핑으로 만든 기존 아카이브(19,301경주)와
API를 **전 기간 월 단위로 대조**했다(복승식 셀 수 기준).

73개월이 불일치했으나, 그중 상당수는 설계상 범위 밖이다.

| 구분 | 월 수 | 셀 차이 | 성격 |
| --- | ---: | ---: | --- |
| 2016-01~05 | 15 | +62,607 | 아카이브 설계 범위 밖 (삼쌍승 도입 이후만 수집) |
| 2016-06 | 3 | +2,694 | 경계월 (6/10부터 수집) |
| **나머지** | **55** | **+19,407** | **실제 누락** |

실제 누락 19,407셀은 복승 기준 경주당 약 50셀이므로 **약 390경주**,
전체 19,301경주의 **약 2%**에 해당한다.

**모든 불일치에서 API가 더 많았다.** 반대 방향은 한 건도 없다.

연도별 실제 누락 월수: 2016:4 / 2017:3 / 2018:12 / 2019:6 / 2022:6 / 2023:14 /
2024:2 / 2025:8. 특정 시기에 몰려 있지 않으므로 **구조적 결함이 아니라 산발적
수집 실패**로 보인다.

또 기존 아카이브에는 **2020·2021년이 통째로 없다**(수집 공백). API는 이 두 해를
정상 반환하므로 복구할 수 있다.

### 시사점

기존 파싱 검증(26개 항목)은 전부 "받아온 것끼리의 정합성"이었다. 애초에 받지
않은 경주는 원리적으로 검출할 수 없었다. 외부 기준선이 없었던 것이다.

**API를 상시 대조 기준선으로 두어야 한다.** 월별 셀 수 대조를 수집 완료
조건에 넣으면 같은 누락이 재발하지 않는다.

## 10. 검증 체크리스트

수집기가 통과해야 할 항목.

- [ ] 경주별 행 수 = 조합 수 (`n`, `n(n-1)`, `C(n,2)`, `C(n,3)`, `n(n-1)(n-2)`)
- [ ] 출주두수는 `API26_2/entrySheet_2`의 `dusu`와 취소마 정보로 독립 산출
- [ ] 복승식을 `API5`와 `API29_1` 양쪽에서 받아 셀 단위 대조
- [ ] 승식별 오버라운드 `Σ(1/O)`가 환급률과 정합
- [ ] 매출액 역산 마권 수가 정수
- [ ] 개최일 판별은 매출액·착순 존재 여부로 (요일 아님)
- [ ] 승식 완전성 검사 — 일부 승식만 있는 날은 플래그
- [ ] 걸러낸 날짜는 삭제하지 않고 별도 보존
- [ ] 월별 `totalCount`를 매니페스트에 기록해 재수집 시 대조
- [ ] 원응답 보존 및 체크섬
