# API227 실제 경주일 기반 수집 설계

*검증일: 2026-08-21*

## 결론

`API227`은 모든 달력 날짜를 순회하지 않는다. 월 단위 `API4_3`을 먼저 수집한 뒤
그 staged 데이터에서 실제 `(meet, rcDate)`를 발견하고, 해당 날짜에 대해서만
`API227`을 호출한다.

이 문서는 `docs/API_FINDINGS.md` 3절의 과거 표현 중
"API227 월 조회의 성능 문제"와 "빈 날짜도 정상 0행으로 보존"이라는 운영 결정을
대체한다. `API227` 공식 요청 계약은 `rc_date` 기반이며 `rc_month`는 공식 요청변수가
아니다. 따라서 `rc_month=202512` 시간초과를 월 데이터량 문제의 증거로 사용하지 않는다.

## 2020-2021 완전수집본 검증

완전수집 원장에는 2020-2021, 3개 경마장의 기존 달력 전수 API227 요청 2,193개가
모두 남아 있다. 이 중 실제 데이터가 있었던 `(meet, date)`는 396개였다.

- 기존 API227 요청: 2,193
- 양수 응답 `(meet, date)`: 396
- 빈 날짜 호출: 1,797
- 빈 호출 비율: 81.94%
- 월 단위 API4_3이 발견한 `(meet, date)`: 396
- API227 양수 날짜 중 API4_3 누락: 0
- API4_3 날짜 중 API227 누락: 0

행 수준에서도 `(meet, date, rcNo, chulNo, hrNo)`를 비교했다.

- API4_3 키: 41,749
- API227 키: 41,749
- API4_3에만 존재: 0
- API227에만 존재: 0

따라서 2020-2021 검증 표본에서는 API4_3이 API227의 실제 경주일 인덱스로 완전히
작동한다.

## 운영 알고리즘

1. 요청 기간의 월 단위 API를 수집한다. `race_record(API4_3)`는 반드시 포함한다.
2. 모든 요청 `meet-month`의 API4_3 ledger 상태가 `complete`인지 확인한다.
3. 각 staged `race_record` JSONL의 `rcDate`를 읽어 `(meet, rcDate)`를 중복 제거한다.
4. 발견된 날짜만 `RequestUnit(endpoint="results", race_date=...)`로 변환한다.
5. 완료된 API227 unit은 ledger에서 제외해 resume한다.
6. 남은 API227 요청 수에 10% 안전여유를 적용해 API227의 일일 3,000회 한도를 검사한다.
7. 한도를 넘으면 수집을 시작하지 않고 기간을 나눈다.

API4_3 수집이 중간에 끊겼다면 API227 단계는 `deferred` 상태로 끝난다. 일부 월만
보고 경주일을 추정하지 않으므로 누락 위험이 없다.

## 2016-2025 호출량

과거 실제 시행일수와 2020-2021 원장 실측을 합친 사전 추정치는 약 2,723개의
`(meet, date)`다. 10% 안전여유를 더하면 약 2,996회로 3,000회 한도 바로 아래다.

그러나 이 숫자는 실행 조건이 아니다. 코드에서는 고정값을 사용하지 않고 API4_3에서
발견된 실제 `N`을 사용한다. 안전율 10%에서 단일 배치가 허용되는 최대 `N`은 2,727이다.

## 구현 원칙

- 기존 `build_units()`의 달력 전수 API227 계획은 2020-2021 파일럿 재현용으로 남긴다.
- 운영 CLI는 `build_monthly_units()` → `discover_result_dates()` →
  `build_result_units()` 순서를 사용한다.
- API4_3 전체 범위가 complete가 아니면 `discover_result_dates()`는 실패하거나 CLI가
  API227 단계를 보류한다.
- raw API227 자체는 유지한다. API4_3과 필드가 완전히 같지 않기 때문이다.
