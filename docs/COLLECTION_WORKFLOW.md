# 수집·검증 워크플로우

*확정 2026-08-21*

이 문서는 KRA 공개 API 수집의 운영 규칙과 단계별 통과 기준을 정한다.
API의 사실관계와 필드 정의는 [API_FINDINGS.md](API_FINDINGS.md), 2020·2021년
범위는 [PILOT_2020_2021.md](PILOT_2020_2021.md), API별 형식·호출량·Dropbox 경로는
[COLLECTION_FORMATS.md](COLLECTION_FORMATS.md)를 따른다. `API227`의 실제 경주일 기반
수집 규칙은 [API227_RACE_DAY_PLANNING.md](API227_RACE_DAY_PLANNING.md)가 과거
`API_FINDINGS.md` 3절의 월 조회 해석보다 우선한다. 특히 개최일을 요일로 거르지 않는다.

## 1. 기본 원칙

1. 계획 승인과 실행 승인을 분리한다. 브랜치 push나 PR 생성은 장시간 API 수집을 시작하지 않는다.
2. 검토 횟수가 아니라 역할을 분리한다. 같은 계획을 반복 검토하지 않는다.
3. 통과 기준을 실행 전에 고정한다. 수집 후 결과에 맞춰 기준을 완화하지 않는다.
4. 원응답을 보존한다. 중복·오류를 정리한 결과만 남겨 원인을 숨기지 않는다.
5. 완료한 작업부터 재개한다. 실패 때문에 검증을 마친 월 또는 날짜를 다시 호출하지 않는다.
6. 증거를 저장소에 남긴다. 채팅이나 일시적인 Actions 로그만을 근거로 삼지 않는다.

## 2. 검토 예산

독립 검토는 최대 4회이며 다음 역할에 배분한다.

| 슬롯 | 대상 | 필수 산출물 |
| --- | --- | --- |
| 1 | 계획 | 범위, 호출량, 식별 규칙, 실패·종료 조건 |
| 2 | 구현 | collector, workflow, 테스트, 비밀·권한 설정 |
| 3 | 결과 | manifest, ledger, 품질보고서, 표본 원응답 |
| 4 | 예비 | 앞선 검토에서 중대 결함이 발견된 경우에만 사용 |

각 지적은 `수용 / 부분 수용 / 기각 / 보류` 중 하나로 기록하고 근거와 검증 결과를 붙인다.
결과 검토자에게 앞선 결론을 정답처럼 제시하지 않는다.

## 3. 실행 단계와 게이트

### 3.1 Evidence probe

본 수집 전에 각 엔드포인트에 최소 요청을 보내 필수 파라미터, 서비스키 인코딩,
응답 스키마, `totalCount`, 페이지 종료 조건, 빈 응답과 오류 응답 형태, 동일 요청의
안정성을 확인한다. probe 결과와 원응답 체크섬을 보존한다.

### 3.2 PR CI

collector와 workflow 변경은 본 수집 전에 다음 검사를 통과해야 한다.

- 구문·정적 검사와 고정 fixture 단위 테스트
- 작은 실제 표본 smoke test
- 페이지 경계·중복·조기 종료 테스트
- schema drift 실패 테스트
- 로그·artifact의 비밀정보 노출 검사
- raw → staged → curated 재생성 테스트

### 3.3 Preflight와 수동 승인

장시간 수집은 `workflow_dispatch`로만 시작하며 GitHub Environment 승인을 요구한다.
preflight는 대상 범위, 예상 요청 수, 완료 단위와 재개 지점, API별 사용 가능량,
출력 경로, collector SHA, schema version, 필요한 Secret의 존재 여부를 출력한다.
Secret 값은 출력하지 않는다.

운영 preflight는 두 단계다.

1. **월 단위 단계**: `API227`을 제외한 API를 계획하고 서비스별 호출 예산을 검사한다.
2. **API227 단계**: 요청 범위의 `API4_3` meet-month가 모두 `complete`가 된 뒤 staged
   `API4_3`에서 `unique(meet, rcDate)`를 만들고, 그 실제 요청 수에 대해 API227 예산을
   다시 검사한다.

일부 `API4_3` 월만 수집된 상태에서는 API227 날짜를 추정하지 않는다. 이 경우 API227
단계는 `deferred`로 끝나며 다음 재개 실행에서 월 단위 수집을 먼저 완료한다.

예상 신규 호출 수와 안전 여유분의 합이 당일 사용 가능량을 넘으면 실행을 차단하고
범위를 분할한다. 완료된 요청은 캐시하여 다시 호출하지 않는다.

## 4. 저장 계층과 데이터 계보

| 계층 | 내용 | 변경 규칙 |
| --- | --- | --- |
| `raw` | 페이지별 API 원응답 바이트 (`.json`/`.xml`) | 불변; 파싱 후 재조립·덮어쓰기 금지 |
| `staged` | 형 변환, 표준 열, 중복 표시 | raw에서 재생성 가능 |
| `curated` | 판정과 품질검사를 통과한 분석 자료 | staged에서 재생성 가능 |

Dropbox 사용자 표시 경로는 `/앱/kra-data/`이며 기존 앱 폴더 아래에 중첩하지 않는다.
각 산출물은 요청 파라미터, collector SHA, schema version, 원천 파일 체크섬과 연결한다.
중복은 raw에서 삭제하지 않는다. staged에서 탐지·분류하고 설명되지 않은 중복이
있으면 해당 수집 단위를 실패 처리한다.

## 5. Ledger와 재개

ledger의 기본 단위는 `경마장 × 월 × API × pool`이다. `API227`만 공식 요청 계약에
맞춰 `경마장 × 실제 경주일 × API`를 기본 단위로 사용하며 `rc_no`는 생략해 해당
날짜의 모든 경주를 한 번에 받는다. 실제 경주일은 모든 요청 `API4_3` meet-month가
완료된 뒤 staged `API4_3`의 `rcDate`에서 발견한다. 모든 달력 날짜를 API227 대상으로
만들지 않는다.

2020·2021 완전수집 파일럿의 과거 달력 전수 계획은 재현성을 위해 legacy planner에만
남겨 둔다. 운영 CLI는 이 경로를 사용하지 않는다.

각 항목에는 요청 파라미터와 페이지 범위, API `totalCount`, raw·고유 행 수,
중복 수와 분류, 오류·재시도 횟수, raw 체크섬, collector SHA, schema version,
품질검사 상태, 시작·완료 시각을 기록한다. 상태는
`pending / running / validating / complete / failed`로 제한한다.

파일 쓰기와 검증이 끝나기 전에 `complete`로 바꾸지 않는다. 임시 경로에 쓴 뒤
검증을 통과한 산출물만 원자적으로 확정한다. 재실행은 완료 단위를 건너뛰고 실패
또는 미완료 단위부터 시작한다. GitHub `run_attempt`는 재개 키로 사용하지 않는다.

## 6. 재시도와 실패 처리

| 오류 | 처리 |
| --- | --- |
| HTTP 429, 5xx, 일시적 네트워크 오류 | 지수 backoff와 jitter를 적용해 제한적으로 재시도 |
| 인증·필수 파라미터 오류 | 즉시 중단 |
| 응답 스키마 변경 | 즉시 중단 |
| 빈 응답 | 정상 빈 기간인지 보조 API로 판정; 자동 성공 금지 |
| 일부 페이지 실패 | 수집 단위 전체를 미완료로 유지 |
| 설명되지 않은 중복 | 실패 처리 |
| 재시도 한도 초과 | 실패 요청 목록에 정확한 파라미터를 보존 |

무제한 반복하지 않는다. 후속 실행은 실패 목록을 입력으로 받아 해당 요청만 재시도한다.
사용자가 재개할 이전 실행을 명시했는데 해당 artifact를 찾지 못하면 새 수집으로
조용히 전환하지 않고 즉시 실패한다.

## 7. 정량 통과 기준

### 7.1 기술적 완전성

- 기본키 중복: 0건
- 설명되지 않은 페이지 경계 중복: 0건
- 필수 열 결측: 0건
- 비정상 HTTP/API 오류가 남은 요청: 0건
- `totalCount = raw 수신 행 수 = 페이지별 행 수 합계`
- API가 중복을 반환하지 않는다는 probe 결과가 유지되면 `totalCount = 고유 행 수`
- 계획에 포함된 ledger 항목 완료율: 100%
- 동일 raw와 같은 코드·schema로 재생성한 staged/curated 체크섬: 동일
- 예상하지 않은 schema 변화: 0건

`totalCount` 일치만으로 중복과 누락이 모두 없다고 단정하지 않는다. 같은 수의 중복과
누락이 상쇄될 수 있으므로 기본키·페이지 경계·고유 수를 별도로 검사한다.

### 7.2 의미적 완전성

- 경주별 승식 행 수가 출주두수 기반 이론 조합 수와 일치
- 출주두수는 출전표와 취소마 정보로 독립 산출
- API5와 API29_1 복승 셀 단위 일치
- 오버라운드와 공시 환급률의 정합성
- 매출액·당첨배당 역산 검산
- 실제 개최일의 승식 완전성
- 매출액·착순을 이용한 개최일 판정
- 제외·보류 날짜를 삭제하지 않고 별도 보존
- 연도·경마장·월별 건수를 KRA 공식 집계 또는 독립 출처와 대조하고 차이를 설명

2020·2021년 코로나 중단으로 인한 빈 기간은 오류가 아니다. 다만 빈 응답을 자동으로
정상 처리하지 않고 매출액·착순·출전표로 근거를 남긴다.

## 8. 증거 묶음

각 본 수집 실행은 실행 manifest와 ledger, collector·workflow SHA, 입력 범위와
요청 파라미터, API 사용량·재시도·실패 목록, raw 체크섬, 데이터 프로파일과
품질보고서, 제외·보류 판정표, 검토 지적 처리표를 지속 가능한 artifact로 남긴다.
Actions 로그가 만료되어도 이 묶음만으로 실행과 판단을 재구성할 수 있어야 한다.

## 9. 종료 조건

다음을 모두 만족할 때만 본 수집을 완료한다.

- 계획·구현·결과 검토에서 미해결 중대 지적 0건
- 사전 정의한 기술·의미 검사가 모두 통과
- 실패 요청 0건
- 대상 ledger 항목 100% `complete`
- raw에서 staged와 curated 재생성 성공
- 문서의 규칙과 구현이 일치
- 남은 경미한 지적이 데이터나 연구 결론에 영향을 주지 않음

완료 판정은 검토 횟수가 아니라 기계적 기준과 독립 결과 검토를 모두 만족했는가로 결정한다.
