# KRA 공개 경마데이터 재수집 계획

## 1. 목표

2020·2021년 공백을 우선 복구하고, 같은 파이프라인으로 전 기간을 처음부터 다시
수집할 수 있는 공개 데이터셋을 만든다. 공공데이터포털 KRA OpenAPI를 정본으로
사용하고, API에 없는 필수 사실만 KRA 공식 사이트에서 보완한다.

2020·2021년은 경주 시행과 국내 발매가 분리될 수 있으므로 다음을 별도로 기록한다.

- 경주가 예정되었는가
- 실제 시행되었는가
- 국내 마권 매출이 있었는가
- 승식별 전체 배당격자가 생성되었는가

경주가 시행됐으나 국내 발매가 없었던 경우는 결측이나 수집 실패가 아니다.

## 2. 2026-08-18 동결 API 사양

Base URL은 `https://apis.data.go.kr/B551015`이다. 공통 파라미터는 다음과 같다.

- `serviceKey`
- `pageNo`
- `numOfRows`: 확인된 최대 3,000
- `_type=json`
- `meet`: 1 서울, 2 제주, 3 부산경남, 4 영천
- `rc_date`: YYYYMMDD
- `rc_month`: YYYYMM
- `rc_no`

Decoding 서비스키를 HTTP 클라이언트가 한 번만 URL 인코딩하도록 한다. 이미
Encoding된 키에 `--data-urlencode` 등을 적용해 `%`가 이중 인코딩되는 경로는
테스트로 차단한다. 서비스명과 operation에 `_1` 접미사가 함께 필요한 경우를
엔드포인트 레지스트리에 그대로 기록한다.

### 2.1 배당 전체격자

| 자료 | 엔드포인트 | 승식 | 역할 |
|---|---|---|---|
| 단일마 격자 | `API28_1/singlePredictionRateInfo_1` | 단승·연승 | 1차 수집원 |
| 두 마리 격자 | `API29_1/doublePredictionRateInfo_1` | EXA·QNL·QPL | 1차 수집원 |
| 세 마리 격자 | `API30_1/triplePredictionRateInfo_1` | TLA·TRI | 1차 수집원 |
| 복승 중복자료 | `API5/quinellaOddsInfo` | 복승 | 교차검증 |
| 통합 확정배당 | `API160_1/integratedInfo_1` | 전체 승식 | 교차검증·보완 |
| 종합 확정배당 | `API301/Dividend_rate_total` | 전체 승식 | 교차검증·보완 |

검증된 예시는 10두 TRI 720행, 11두 TRI 990행, 12두 TRI 1,320행이다. API에도
`9999.9` 상한이 존재하므로 원문값과 `is_capped`를 함께 저장하고 실제값으로
간주하지 않는다.

### 2.2 부가자료

| 엔드포인트 | 수집 내용 |
|---|---|
| `API179_1/salesAndDividendRate_1` | 승식별 매출액 `amt`, 당첨조합, 확정배당; 통상 경주당 7행 |
| `API26_2/entrySheet_2` | 출전표와 등록두수 `dusu`; 하루 단위 응답 |
| `API214_1/RaceDetailResult_1` | 착순, 날씨, 주로, 단승·연승 배당 |
| `API4_3/raceResult_3` | 경주기록 |

2020·2021년은 위 API에서 정상 반환되는 것이 확인됐다. 기존 아카이브의 공백은
API 수집으로 복구 가능하다.

## 3. 자료원 우선순위

1. API26·API214·API4로 경주 우주와 실제 시행 여부를 구축한다.
2. API179로 국내 발매와 승식별 매출 존재를 판정한다.
3. API28·API29·API30으로 전체 배당격자를 수집한다.
4. API5·API160·API301과 적중조합 정보를 교차검증한다.
5. 필수 필드가 모든 관련 API에서 실제 누락된 경우만 KRA 사이트를 스크래핑한다.

제3자 자료는 정본으로 사용하지 않는다. API와 KRA 사이트가 충돌하면 어느 한쪽을
덮어쓰지 않고 두 원문과 충돌상태를 보존한다.

## 4. 경주와 승식 상태

모든 경주와 승식은 다음 상태 중 하나를 가져야 한다.

| 상태 | 의미 |
|---|---|
| `not_held` | 예정되었지만 공식 결과가 없어 시행되지 않음 |
| `held_no_domestic_market` | 결과는 있으나 국내 승식별 매출과 배당격자가 없음 |
| `held_market_complete` | 매출이 있고 API 격자가 완전함 |
| `held_api_incomplete` | 매출이 있으나 관련 API 격자가 불완전함 |
| `held_source_conflict` | 공식 API 간 또는 API와 사이트가 상충함 |
| `unresolved_transport` | 재시도 후에도 전송 실패가 해결되지 않음 |

정상 응답 0행만으로 무발매를 선언하지 않는다. 공식 결과, API179 매출,
API28~30 격자 존재를 함께 사용한다.

## 5. 수집 단계

### 5.1 경주 인벤토리

1. 2020·2021년의 날짜×경주장별 출전표와 경주결과를 수집한다.
2. `(rc_date, meet, rc_no)` 경주키를 정규화한다.
3. API26의 등록두수, API214의 실제 출주마, 취소·제외마를 구분한다.
4. API179로 승식별 매출이 양수인지 확인한다.
5. 연도×월×경주장×시장상태별 경주 수를 동결한다.

이 단계가 끝나면 실제 경주 수와 페이지 수를 이용해 총 호출예산과 예상용량을
확정한다.

### 5.2 조종 수집

다음 층의 첫 날짜·마지막 날짜와 최소 2개 발매일을 선택한다.

- 연도×경주장
- 발매·무발매 상태
- 취소·제외마 유무
- 작은·중간·큰 출전두수
- `9999.9` 포함 여부

2019년 말과 2022년 초의 기존 아카이브 표본도 API 자료와 비교하여 자료원 변경이
조합 방향, 배당 정밀도, 매출 단위에 영향을 주지 않는지 확인한다.

### 5.3 전체 격자 수집

API28·29·30을 페이지 끝까지 받고 다음 불변식을 검사한다.

- 내려받은 행 수 = `totalCount`
- 중복 조합키 0건
- 조합 내부의 동일 마번 반복 0건
- 모든 행에 승식·조합·배당·경주키 존재
- 매출이 양수인 승식의 support가 완전함

활성 출주마가 \(n\)두일 때 기대 support는 다음과 같다.

| 승식 | 기대 행 수 |
|---|---:|
| 단승·연승 | 각 \(n\) |
| 복승 | \(\binom{n}{2}\) |
| 쌍승 | \(n(n-1)\) |
| 복연승 | \(\binom{n}{2}\) |
| 삼복승 | \(\binom{n}{3}\) |
| 삼쌍승 | \(n(n-1)(n-2)\) |

API28이 단승·연승을 함께 반환하면 승식별로 분리해 각 support를 검사한다.
API29·30도 pool별로 분리한다. 취소마는 API214의 최종 실제 출주마 집합에서
제외한다. 2025-03-08 서울 사례처럼 하루 단위 집계도 경주별 실제 출주두수에서
계산한 합과 비교한다.

### 5.4 매출·환급률·적중조합 검증

- API179의 승식별 매출과 배당격자 존재를 대조한다.
- 실제 적중조합이 전체 격자 안에 존재하는지 확인한다.
- 미검열 적중배당을 API160·API301과 비교한다.
- 환급률 가정은 고정 상수가 아니라 연도·승식별 공식 규정 메타데이터로 저장한다.
- 알려진 삼쌍승 0.73, 단승 0.80 역산 정합성은 조종 표본 회귀테스트로 둔다.
- `9999.9`에서는 정수 마권수를 점식별한 것으로 보고하지 않는다.

### 5.5 조건부 스크래핑

다음 조건을 모두 충족할 때만 KRA 공식 사이트를 스크래핑한다.

1. 경주가 시행됐고,
2. 해당 승식 매출이 양수이며,
3. API28~30과 교차검증 API가 모두 필수자료를 완전하게 제공하지 않고,
4. 서로 다른 시점의 재조회로 일시적 장애가 아님을 확인한 경우.

차단을 우회하지 않는다. 원본 HTML·이미지는 이용조건 확인 전 공개하지 않고,
URL·조회시각·응답상태·SHA-256과 추출한 사실값을 별도로 기록한다.

## 6. 호출 한도와 재시작

- 개발계정 일일 한도 3,000회
- 내부 운영 상한 2,500회, 500회는 재시도·검증용으로 유보
- `numOfRows=3000`을 우선 사용하되 응답 안정성을 조종 단계에서 확인
- 최대 동시 요청 2개
- 성공 원응답 저장 후에만 ledger를 완료 처리
- 동일 요청의 확인된 체크섬이 있으면 재호출하지 않음
- 429·5xx·timeout만 지수형 재시도하고 `Retry-After` 준수
- 정상 0행은 자동 재시도하지 않고 시장상태 판정으로 보냄
- 날짜·경주장·엔드포인트·페이지 단위로 중단 지점부터 재개

## 7. 저장과 공개

### 7.1 GitHub 저장소

다음을 버전관리한다.

```text
src/                    수집·정규화·검증 코드
config/                 엔드포인트와 스키마 설정
tests/                  단위·속성·회귀테스트
plans/                  동결 계획
manifests/              파일·행·호출·체크섬 목록
reports/                품질·누락·충돌 보고서
```

### 7.2 공개 데이터 릴리스

대용량 자료는 Git 커밋에 넣지 않고 버전된 공개 Release 자산으로 배포한다.

```text
raw-openapi-YYYY-vN.tar.zst       변경하지 않은 API 원응답
normalized-YYYY-vN.parquet        정규화 표
manifest-YYYY-vN.json             파일·행·스키마·provenance
SHA256SUMS                         무결성 검증
```

로컬·Dropbox 경로는 공개 매니페스트에 쓰지 않는다. API 인증키와 Actions Secret은
절대 공개하지 않는다. API별 원자료 이용조건과 한국마사회·공공데이터포털 출처를
`DATA_LICENSE.md`에 기록한다. KRA 웹 원문은 별도 이용허락이 확인되기 전에는
공개 Release에서 제외한다.

## 8. 품질보증과 완료 기준

다음을 모두 만족해야 연도 파티션을 공개한다.

1. 모든 공식 시행 경주에 상태와 provenance가 있음
2. 모든 양수 매출 승식에 완전한 격자 또는 명시적 예외가 있음
3. 무발매가 API 누락이나 0배당으로 오분류되지 않음
4. 원응답 행 수, 정규화 행 수와 매니페스트 행 수가 일치함
5. 경주·조합키 중복과 충돌이 0건임
6. 취소·제외마 처리 뒤 이론 support가 일치함
7. API179와 배당 API의 시장 존재 판정이 일치하거나 충돌표에 남음
8. `9999.9`가 검열값으로 보존됨
9. 원응답과 공개 자산의 SHA-256 검증이 통과함
10. 네트워크 없는 검증 명령이 보고서를 재생성함
11. 2020·2021년과 정상연도의 제도 차이를 데이터 변수로 보존함
12. Claude Opus 5의 필수 지적이 해결되거나 저자결정 사항으로 명시됨

## 9. Claude 독립검토

검토 모델은 `claude-opus-5`, 한 PR의 성공 검토 상한은 4회다. 실패한 Actions
실행은 횟수에 포함하지 않는다.

- 1회차: API 사양·경주 우주·발매/무발매 식별
- 2회차: 호출예산·재시작·원응답 보존·공개 라이선스
- 3회차: support·취소마·검열·자료원 충돌·연도 연결
- 4회차: 남아 있는 중대 문제의 최종 검토

각 회차 뒤 필요한 지적만 반영한다. 포함규칙, 식별가정, 공개범위 변경은 자동
반영하지 않고 저자결정 사항으로 구분한다. Claude는 파일 수정·커밋·병합을 하지
않는다.
