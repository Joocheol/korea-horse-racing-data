# KRA 공개 경마데이터 재수집 계획

## 1. 범위와 산출물

v1은 **2020-01-01~2021-12-31**의 KRA 경주를 처음부터 다시 수집해 공백을
복구한다. 다른 연도는 동일한 파이프라인을 쓰되 별도 릴리스로 다룬다. 수집의
정본은 공공데이터포털 KRA OpenAPI이며, API로 판정할 수 없는 필수 사실만 KRA
공식 사이트·공식 공고에서 보완한다.

수집 모집단과 분석 표본을 분리한다. 수집층에는 시행·무발매·불완전·증거부족
상태를 모두 1급 레코드로 공개하고, 분석층은 연구 질문별 포함·제외 규칙을 별도
버전으로 선언한다. 무발매나 증거부족 레코드를 조용히 삭제하지 않는다.

각 경주에 대해 다음을 서로 다른 변수로 기록한다.

- 예정 여부와 근거
- 실제 시행 여부와 근거
- 국내 승식별 매출 존재 여부
- 승식별 전체 조합격자 존재 여부
- 격자 값의 의미론: `unverified_snapshot`, `prediction_snapshot`, `final_snapshot`

경주가 시행됐으나 국내 발매가 없었던 경우는 결측이나 수집 실패가 아니다.

## 2. 2026-08-18 동결 API 사양

Base URL은 `https://apis.data.go.kr/B551015`이다. 공통 파라미터 후보는 다음과
같다.

- `serviceKey`
- `pageNo`
- `numOfRows`: 확인된 최대 3,000
- `_type=json`
- `meet`: 1 서울, 2 제주, 3 부산경남, 4 영천
- `rc_date`: YYYYMMDD
- `rc_month`: YYYYMM
- `rc_no`

Decoding 서비스키를 HTTP 클라이언트가 한 번만 URL 인코딩한다. 최종 전송값은
Decoding 키의 1회 퍼센트 인코딩과 바이트 단위로 같아야 하고 `%25`가 없어야 하며,
키 안의 `+`, `/`, `=`는 각각 인코딩되어야 한다. Encoding 키를 다시 인코딩하는
경로는 테스트에서 실패시킨다.

### 2.1 배당 격자와 교차검증

| 자료 | 엔드포인트 | 승식 | v1 역할 |
|---|---|---|---|
| 단일마 격자 | `API28_1/singlePredictionRateInfo_1` | 단승·연승 | 전체 조합 1차 수집원 |
| 두 마리 격자 | `API29_1/doublePredictionRateInfo_1` | EXA·QNL·QPL | 전체 조합 1차 수집원 |
| 세 마리 격자 | `API30_1/triplePredictionRateInfo_1` | TLA·TRI | 전체 조합 1차 수집원 |
| 복승 중복자료 | `API5/quinellaOddsInfo` | 복승 | 교차검증 |
| 통합 확정배당 | `API160_1/integratedInfo_1` | 전체 승식 | 적중조합 교차검증·보완 |
| 종합 확정배당 | `API301/Dividend_rate_total` | 전체 승식 | 적중조합 교차검증·보완 |

2026-08-18 실측에서 10두 TRI 720행, 11두 TRI 990행, 12두 TRI 1,320행으로
전체 순서조합 수와 일치했고 `9999.9` 상한도 확인됐다. 다만 operation명의
`PredictionRate`만으로 확정/예상을 단정하지 않는다. 조종 수집에서 같은 경주의
적중조합을 API179·API160·API301의 확정배당과 비교하고 응답의 시각·확정 플래그를
기록한 뒤 `odds_semantics`를 확정한다. 의미론이 다르면 수치 충돌이 아니라 별도
측정치로 보존한다. 충돌키는 `(경주키, 승식, 조합, 필드, 자료원, 시점)`이다.

### 2.3 엔드포인트 레지스트리

수집 전에 `config/endpoints.yml`에서 각 operation을 다음 스키마로 동결한다.

```yaml
service: API30_1
operation: triplePredictionRateInfo_1
query_grain: race
required_params: [meet, rc_date, rc_no, pageNo, numOfRows, _type]
optional_params: []
response_root: response.body.items.item
success_codes: ["00", "0000"]
pagination: {page: pageNo, size: numOfRows, total: totalCount, max_size: 3000}
market_field: pool
market_codes: {TLA: trifecta_box, TRI: trifecta_ordered}
```

위 값은 예시이며, 각 엔드포인트의 필수·선택 파라미터, 날짜/월/경주 입도,
응답 루트, 성공코드, 코드사전과 실제 서버 상한을 조종 단계에서 실측해 확정한다.
서비스명과 operation의 `_1` 접미사도 문자 그대로 저장한다. 재개키는
`(endpoint_id, canonical_params_without_serviceKey, pageNo)`이며 파라미터 전체의
SHA-256을 함께 둔다. 경주 단위 요청에는 `rc_no`가 반드시 포함된다.

## 3. 자료원 우선순위와 독립 분모

1. KRA 공식 시행계획·변경/취소·발매중지 공고로 날짜×경주장의 열거 분모를 만든다.
2. API26·API214·API4로 경주 목록과 실제 시행 여부를 구축한다.
3. API179로 국내 발매와 승식별 매출 존재를 판정한다.
4. API28·API29·API30으로 전체 조합격자를 수집한다.
5. API5·API160·API301과 적중조합 정보를 교차검증한다.
6. 필수 사실이 관련 API에서 실제 누락된 경우에만 KRA 사이트를 조회한다.

1번의 공식 공고는 배당 정본이 아니라 API 결측을 탐지하기 위한 독립적인 열거
분모다. 제3자 자료는 정본으로 사용하지 않는다. 공식 자료끼리 충돌하면 어느
한쪽도 덮어쓰지 않고 원문·시점·충돌상태를 보존한다.

## 4. 경주와 승식 상태

모든 열거 대상은 다음 상태 중 하나를 가진다.

| 상태 | 의미 |
|---|---|
| `not_held` | 공식 예정 근거는 있으나 취소 공고 또는 결과 부재의 독립 증거로 미시행 확정 |
| `held_no_domestic_market` | 시행 결과가 있고 국내 해당 승식의 무발매 근거가 확인됨 |
| `held_market_complete` | 매출이 있고 API 격자가 검증된 support 규칙에 따라 완전함 |
| `held_api_incomplete` | 매출이 있으나 관련 API 격자가 불완전함 |
| `held_source_conflict` | 같은 의미·시점의 공식 자료가 허용오차 밖에서 상충함 |
| `evidence_insufficient` | 시행은 확인됐지만 발매 여부 또는 격자 완전성 증거가 부족함 |
| `unresolved_transport` | 인증·쿼터·점검·스키마·전송 오류가 재시도 뒤에도 미해결 |

HTTP 2xx나 0행만으로 무발매를 선언하지 않는다. 모든 상태는 상태값뿐 아니라
판정에 사용한 evidence 레코드와 규칙 버전을 가진다.

## 5. 수집 단계

### 5.1 경주 인벤토리

1. 2020·2021년의 공식 시행계획·변경 공고를 날짜×경주장 분모로 동결한다.
2. 날짜×경주장별 API26·API214·API4 자료를 수집한다.
3. `(rc_date, meet, rc_no)` 경주키를 정규화한다.
4. 등록·출전예정·발주·발매전취소·발매후제외·실격·낙마·중지를 별도 플래그로 둔다.
5. API179로 승식별 매출행과 `amt`를 확인한다.
6. 연도×월×경주장×시장상태별 경주 수를 동결한다.

`started_set`은 착순 유무가 아니라 발주 참가를 나타내는 공식 필드로 정의한다.
실격·낙마·경주중지는 발주했다면 제외하지 않는다. 사용할 필드와 코드의 실제
의미는 엔드포인트 레지스트리에 근거와 함께 고정한다.

### 5.2 조종 수집

각 연도×경주장의 첫·마지막 날짜와 최소 2개 발매일을 포함하고 다음 층을 의도적으로
표집한다.

- 발매·무발매·증거부족
- 발매전취소·발매후제외·실격·낙마
- 소두수·중간·대두수 경주와 승식 미제공 사례
- `9999.9`, 0, null, 조합행 부재 사례
- API28~30 적중조합과 확정배당 자료의 비교 가능 사례

2019년 말과 2022년 초의 표본도 비교한다. 조종 종료 전 다음을 확정한다.

- API28~30 격자의 시점 의미와 0표 조합 표현 방식
- `numOfRows` 1·100·1000·3000 결과 합집합의 동일성
- 엔드포인트별 실제 HTTP 상태, content-type, 성공·인증오류·점검·쿼터 코드
- 일일 한도의 적용 단위와 호출예산 계수

한도초과를 만들기 위해 운영 키의 쿼터를 고의 소진하지 않는다. 공식 오류규격,
기존 오류 fixture 또는 격리된 최소 요청으로 확인하고 미확인 항목은 미확인으로
남긴다.

### 5.3 응답 봉투와 페이지네이션

정상 응답은 다음 네 조건을 모두 만족해야 한다.

1. HTTP 2xx
2. 기대한 JSON content-type과 파싱 가능한 본문
3. 레지스트리의 성공 `resultCode`
4. 엔드포인트 스키마 검증 통과

HTTP 200의 한도초과·키 오류·점검 코드, JSON 요청에 대한 XML 오류, HTML 오류와
스키마 불일치는 0행으로 바꾸지 않고 `unresolved_transport` 경로로 보낸다.
재시도 가능 코드와 즉시 중단할 인증오류는 레지스트리에서 구분한다.

페이지별 원응답을 저장하며 다음을 검사한다.

- 모든 페이지의 `totalCount`가 동일함; 변하면 요청 전체를 새 스냅샷으로 재수집
- 실제 반환 행 수와 페이지 번호로 진행하고 같은 요청키의 페이지 교집합이 0건임
- 합집합 행 수가 `totalCount`와 같고 정규화키 중복이 0건임
- 계산된 마지막 페이지 다음 한 페이지가 정상 0행임

### 5.4 조합 support

격자 행에는 승식·조합·배당·경주키가 있어야 하고 조합 안에 같은 마번이 반복되면
안 된다. 이론 support의 기준 집합은 조종에서 확인된 API 격자 생성 규칙에 따라
`started_set` 또는 `sales_open_set` 중 하나로 버전 고정한다.

| 승식 | 이론 support |
|---|---:|
| 단승·연승 | 각 \(n\) |
| 복승·복연승 | 각 \(\binom{n}{2}\) |
| 쌍승 | \(n(n-1)\) |
| 삼복승 | \(\binom{n}{3}\) |
| 삼쌍승 | \(n(n-1)(n-2)\) |

승식 제공 여부는 두수만으로 추정하지 않고 API179의 승식행·매출과 공식 규칙으로
판정한다. 발매전취소와 발매후제외가 support에 미치는 영향은 별도 규칙표로 둔다.
0표 조합이 행으로 제공되는지 조종에서 확인하기 전까지 완전성 불변식은
`observed_support ⊆ theoretical_support`만 강제한다. 확인 뒤 승식·기간별로 `=` 또는
`⊆`를 선언하며, 미상 불일치는 결측이 아니라 규칙 미확인으로 남긴다.

### 5.5 매출·환급률·검열·충돌 검증

- API179의 승식별 매출과 격자 존재를 대조한다.
- 실제 적중조합이 전체 격자에 존재하는지 확인한다.
- 동일 의미론·시점의 미검열 적중배당만 API179·API160·API301과 비교한다.
- 정상값, 상한검열 `9999.9`, 0, null, 행 부재를 별도 sentinel로 저장하고 조종에서
  의미를 확정한다.
- 배당에서 마권수를 역산할 때 모든 값은 절사·반올림·최저배당 때문에 구간추정으로
  취급한다. `9999.9`는 실제값이 아닌 상한 sentinel이며 식별 가능한 경계만 보고한다.

환급률 메타데이터는 `(승식, 적용시작일, 적용종료일, 값, 공식 근거문서 식별자,
확인일)`로 저장한다. 삼쌍승 0.73·단승 0.80 역산 검사는 허용오차를 명시하고,
최저배당 구속·반환·절사 사례는 예외 플래그로 남긴다.

### 5.6 조건부 KRA 사이트 조회

다음 두 게이트 중 하나를 만족할 때만 공식 사이트를 조회한다.

- 시행·발매 분모 게이트: 공식 API만으로 예정/시행/발매 여부를 판정할 수 없음
- 자료 보완 게이트: 시행과 양수 매출은 확인됐으나 관련 API가 필수 필드를 완전하게
  제공하지 않고, 서로 다른 시점의 재조회로 일시 장애가 아님

조회 전에 robots 정책과 해당 페이지 이용조건을 기록한다. 차단·인증을 우회하지
않고, 식별 가능한 User-Agent, 동시 1개, 요청 간 최소 2초, 초기 상한 100회/일을
적용하며 403·429에는 중단한다. 전체 URL 대신 비밀값을 뺀 정규화 파라미터와
파라미터 해시, 조회시각, 응답상태, 원문 SHA-256을 기록한다.

이용조건이 확인되지 않은 HTML·PDF·이미지는 비공개 격리 저장소에서 최대 90일만
보존하고 공개하지 않는다. 확인 뒤 허용된 원문만 공개하며, 그렇지 않으면 검증된
사실값·provenance·추출 규칙만 유지하고 원문은 보존기간 종료 뒤 폐기한다.

## 6. 호출예산, 오류처리와 재시작

- 개발계정 일일 한도: 3,000회
- 내부 운영 상한: 2,500회; 500회는 인벤토리·검증·재시도용
- 최대 동시 요청 2개
- 성공 원응답 저장 뒤에만 ledger 완료 처리
- HTTP 429·5xx·timeout과 레지스트리의 재시도 가능 본문코드는 지수형 재시도하고
  `Retry-After`를 지킨다.
- 인증·스키마 오류는 무한 재시도하지 않고 중단한다.

v1 총호출은 인벤토리 뒤 다음 식으로 동결한다.

\[
C = C_{calendar}+C_{inventory}+\sum_r(P_{28,r}+P_{29,r}+P_{30,r}
+P_{179,r}+P_{214,r}+P_{4,r})+C_{crosscheck}+C_{pilot}+C_{retry}
\]

각 \(P\)는 실제 페이지 수이며 API5·160·301, 오류 확인, 다음 빈 페이지도 해당
항목에 포함한다. `C_retry`는 기초 호출의 20%를 상한으로 예약한다. 예상 최소
운영일은 `ceil(C / 2500)`이고 일별 500회 유보분을 침범하지 않는다. 경주 수,
엔드포인트별 페이지 분포, `C`, 예상 운영일과 저장용량을 승인 가능한 preflight
보고서로 만들기 전에는 본수집을 시작하지 않는다. 전 기간 재수집은 v1 예산에
포함하지 않는다.

저장된 요청의 재개키는 `(endpoint_id, canonical_params_without_serviceKey,
pageNo)`다. 동일 요청키와 동일 원문 해시가 있으면 건너뛴다. 공식 정정·심판변경,
스키마 버전 변경, 명시적 재수집 요청은 새 스냅샷을 추가하는 트리거다.

## 7. 저장, 무결성과 공개

### 7.1 GitHub 저장소

코드·설정·테스트·계획·매니페스트·보고서만 Git에 버전관리한다.

```text
src/                    수집·정규화·검증 코드
config/                 엔드포인트·오류코드·스키마·support 규칙
tests/                  단위·속성·회귀테스트와 비밀누출 테스트
plans/                  동결 계획
manifests/              파일·행·호출·개별 원응답 체크섬 목록
reports/                품질·누락·충돌·preflight 보고서
```

### 7.2 공개 Release 자산

```text
raw-openapi-YYYY-vN.tar.zst       변경하지 않은 성공 API 원응답
normalized-YYYY-vN.parquet        정규화 표
manifest-YYYY-vN.json             요청키·개별 원응답 SHA-256·행·스키마·provenance
SHA256SUMS                         배포파일 전송 무결성용 해시
DATA-LICENSE-YYYY-vN.txt          해당 파티션의 적용 이용조건·출처
```

정본 무결성은 매니페스트의 `request_key → raw byte SHA-256`이다. 아카이브 해시는
전송 편의용이다. tar는 경로 정렬, 고정 mtime, uid/gid 0과 정규화 권한을 사용하고,
zstd 버전·레벨과 생성 명령을 매니페스트에 기록한다.

원응답은 append-only다. 정정 때 새 스냅샷을 추가하고 이전 판을 삭제하지 않으며,
릴리스 매니페스트에 `supersedes` 관계와 재수집 사유를 둔다. 단, 공개 권리가 없는
KRA 웹 원문은 이 append-only 공개 규칙의 대상이 아니다.

저장되는 요청 식별자에서 `serviceKey`를 제거하고 로그·오류 본문·원응답 저장 직전
알려진 비밀값을 마스킹한다. 공개 전 커밋 이력과 모든 Release 자산을 비밀문자열
스캔한다. 로컬 경로·Dropbox 경로·Secret은 공개하지 않는다.

## 8. 라이선스·출처 게이트

코드는 MIT License다. 데이터는 프로젝트가 임의로 일괄 재라이선스하지 않고,
각 원자료의 공식 이용허락범위와 출처표시 조건을 승계한다. 연도 파티션에 기여한
모든 엔드포인트에 대해 `(endpoint, 이용허락범위, 확인일, catalog URL)`이 확인되고
원문·정규화 데이터 재배포가 허용돼야 공개한다. 하나라도 미확인이면 자료 공백을
감수하고 그 source를 제외하거나 파티션 공개를 보류한다.

각 Release의 `DATA-LICENSE`에 가장 제한적인 적용조건, KRA·공공데이터포털 출처,
확인일과 카탈로그 URL을 기록한다. KRA 웹 원문은 별도 허용이 확인되기 전 공개
Release에서 제외한다.

## 9. 품질보증과 완료 기준

다음을 모두 만족해야 연도 파티션을 공개한다.

1. 공식 열거 분모의 모든 대상에 상태·evidence·provenance가 있음
2. 양수 매출 승식에 검증된 support 규칙상의 완전한 격자 또는 명시적 예외가 있음
3. 무발매·증거부족·전송오류가 서로 오분류되지 않음
4. 성공 봉투, 원응답 행 수, 정규화 행 수와 매니페스트 행 수가 일치함
5. 경주·조합키 중복은 0건이며 자료원 충돌은 충돌표에 보존됨
6. 취소·제외·실격·낙마 규칙과 support 검사가 일치함
7. API179와 배당 API의 시장 존재 판정이 일치하거나 충돌표에 남음
8. `9999.9`·0·null·행 부재 sentinel이 구별됨
9. 모든 개별 원응답과 공개 자산의 SHA-256 검증이 통과함
10. 네트워크 없는 한 명령으로 정규화·품질보고서가 재생성됨
11. 2020·2021년과 정상연도의 제도 차이가 데이터 변수로 보존됨
12. 기여한 모든 엔드포인트의 재배포 조건이 확인됨
13. 공개 커밋·로그·매니페스트·Release의 비밀문자열 스캔이 통과함
14. 수집 모집단과 분석 표본의 포함·제외 규칙이 별도 산출물로 존재함
15. Claude Opus 5의 필수 지적이 해결되거나 저자결정으로 명시됨

## 10. Claude 독립검토

검토 모델은 `claude-opus-5`, 한 PR의 성공 검토 상한은 4회다. 실패한 Actions
실행은 횟수에 포함하지 않는다.

- 1회차: API 사양·경주 우주·발매/무발매 식별
- 2회차: 호출예산·재시작·원응답 보존·공개 라이선스
- 3회차: support·취소마·검열·자료원 충돌·연도 연결
- 4회차: 남은 중대 문제의 최종 검토

각 회차 뒤 필요한 지적을 반영해 새 커밋으로 다음 회차를 요청한다. Claude는 파일
수정·커밋·병합을 하지 않는다. 4회 안에 HIGH 지적이 남으면 본수집 착수 대신
저자결정 또는 추가 실측 항목으로 명시한다.
